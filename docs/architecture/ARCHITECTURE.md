# 🏗️ 架构设计文档

> 详细说明多 Agent 协作机制、状态流转、通信方式与失败降级策略。

---

## 1. 总体架构

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| **单一职责** | 每个 Agent 只做一件事,便于独立优化和测试 |
| **工具化子 Agent** | 子 Agent 以 Tool 形式注册给总控,通过统一接口调用 |
| **流式优先** | 全链路支持流式输出,提升用户体感 |
| **多层容错** | 任一环节失败都有降级策略,不导致整体崩溃 |
| **配置驱动** | 所有可调参数通过 `.env` 配置,无需改代码 |

### 1.2 架构分层

```
┌───────────────────────────────────────────────────────────┐
│                      接入层 (Interface)                    │
│   CLI (cli.py)   FastAPI (api.py)   Streamlit (app.py)  │
└─────────────────────────────┬─────────────────────────────┘
                              ↓
┌───────────────────────────────────────────────────────────┐
│                   编排层 (Orchestration)                    │
│              Orchestrator Agent (Router + State)            │
│     意图识别 → 路由决策 → 子 Agent 调度 → 结果整合           │
└──────┬──────────────┬──────────────┬──────────────┬───────┘
       ↓              ↓              ↓              ↓
┌───────────┐  ┌───────────┐  ┌───────────┐  ┌───────────┐
│  SQL      │  │  RAG      │  │  Analyst  │  │  Visualizer│
│  Agent    │  │  Agent    │  │  Agent    │  │  (工具类)  │
└─────┬─────┘  └─────┬─────┘  └───────────┘  └───────────┘
      ↓               ↓
┌───────────┐  ┌───────────┐
│ Schema    │  │ Vector    │
│ Agent     │  │ Store     │
└─────┬─────┘  └─────┬─────┘
      ↓               ↓
┌───────────────────────────────────────────────────────────┐
│                    数据层 (Data)                           │
│   SQLite (finance.db)     FAISS (faiss_index)              │
│   文档文件 (data/docs/)                                    │
└───────────────────────────────────────────────────────────┘
```

## 2. 多 Agent 协作机制

### 2.1 Agent 清单与职责

| Agent | 类型 | 输入 | 输出 | 依赖 |
|-------|------|------|------|------|
| **Orchestrator** | 总控 | 用户自然语言查询 | 完整投研报告(Markdown) | SQL Agent / RAG Agent / Analyst Agent |
| **Schema Agent** | 工具型 | - | 数据库 schema 描述文本 | db_client |
| **SQL Agent** | 专家型 | 用户问题 + schema 描述 | 可执行 SQL + 执行结果 | Schema Agent / Executor |
| **Retriever Agent** | 专家型 | 用户查询 | 召回的文档片段列表(带元数据) | VectorStore |
| **Analyst Agent** | 专家型 | SQL 结果 + RAG 证据 | 投研分析报告(Markdown) | LLM |

### 2.2 通信方式

#### 2.2.1 工具化调用(Tool-based)

子 Agent 以 `@tool` 装饰的函数形式注册给 Orchestrator Agent,通过 LangChain 的 `create_agent` 实现:

```
Orchestrator Agent
  ├── Tool: query_sql(query: str) -> str
  │     └── 内部调用 SQL Agent.invoke()
  ├── Tool: search_docs(query: str) -> str
  │     └── 内部调用 Retriever Agent.invoke()
  └── Tool: generate_report(data: str) -> str
        └── 内部调用 Analyst Agent.invoke()
```

**优点**:
- Orchestrator 不需要知道子 Agent 的内部实现,只看 Tool 描述
- 子 Agent 可以独立替换/升级,不影响总控
- 天然支持多轮工具调用(LLM 自主决定调用顺序)

#### 2.2.2 事件流通信(Streaming)

通过 LangGraph 的 `astream_events` 实现全链路流式输出:

```
事件类型:
  on_chat_model_stream  → LLM 生成 token,直接 yield 给用户
  on_tool_start         → 工具开始执行,输出状态标记
  on_tool_end           → 工具执行完成,输出完成标记
  on_chain_start/end    → 子 Agent 生命周期事件
```

事件监听在 `Orchestrator._stream_events()` 中统一处理,过滤后输出给用户。

## 3. 状态流转

### 3.1 Orchestrator 状态机

```
           用户输入
              ↓
        ┌────────────┐
        │ 初始化状态  │
        └─────┬──────┘
              ↓
        ┌────────────┐
        │ 路由决策    │ ← Router Agent 判断意图
        └─────┬──────┘
              ├──────────────┬──────────────┐
              ↓              ↓              ↓
        ┌─────────┐   ┌──────────┐   ┌──────────┐
        │SQL 模式  │   │RAG 模式  │   │混合模式  │
        └────┬────┘   └────┬─────┘   └────┬─────┘
             ↓              ↓             ↓
        ┌─────────┐   ┌──────────┐   ┌──────────┐
        │SQL 执行  │   │文档检索  │   │SQL 执行  │
        └────┬────┘   └────┬─────┘   └────┬─────┘
             │              │             ↓
             │              │        ┌──────────┐
             │              │        │文档检索  │
             │              │        └────┬─────┘
             └──────┬───────┘             │
                    ↓                     │
              ┌───────────┐               │
              │ 报告生成   │ ←─────────────┘
              │ (Analyst) │
              └─────┬─────┘
                    ↓
              ┌───────────┐
              │ 结果输出   │
              │ (Markdown) │
              └───────────┘
```

### 3.2 路由决策逻辑

Router 基于用户输入的关键词和语义判断模式:

| 模式 | 触发条件 | 示例 |
|------|---------|------|
| **SQL-only** | 查询明显涉及数字/报表/指标,且无文档关键词 | "近5年营收"、"行业平均ROE" |
| **RAG-only** | 查询明显涉及研报/公告/观点,且无数据指标 | "研报怎么看"、"公告内容" |
| **混合模式** | 同时包含数据查询 + 文档检索特征 | "分析财报+引用研报"、"对比数据+机构观点" |
| **降级为混合** | Router 置信度 < 0.7,无法明确判断 | "茅台怎么样"(模糊查询) |

路由决策由 LLM 完成,输出结构化 JSON:
```json
{
  "mode": "hybrid",
  "confidence": 0.85,
  "reason": "用户同时提到了财报数据和研报观点"
}
```

## 4. 失败分支与降级策略

### 4.1 降级总览

| 失败点 | 触发条件 | 降级策略 | 用户感知 |
|--------|---------|---------|---------|
| **LLM 调用失败** | 超时/限流/网络错误 | 指数退避重试 3 次,仍失败返回错误提示 | 看到"调用失败,已重试 3 次" |
| **DB 连接失败** | 文件不存在/锁定/损坏 | 重连 3 次,仍失败则 SQL 路径不可用 | Router 自动跳过 SQL,仅走 RAG |
| **向量库加载失败** | 索引文件损坏/缺失 | RAG 降级为纯 LLM 知识回答 | 报告中标注"无文档证据,结论仅供参考" |
| **SQL 生成失败** | 语法错误/无法理解问题 | 带错误信息重试 2 次,仍失败返回错误 | Analyst 仅用 RAG 证据分析 |
| **SQL 执行失败** | 运行时错误/超时 | 返回错误信息,不中断主流程 | 报告中说明"部分数据查询失败" |
| **RAG 召回为空** | top-k 全部相似度 < 阈值 | 返回空列表,标注"无相关文档" | 报告中说明"未找到相关研报" |
| **Router 失败** | 输出格式错误/置信度过低 | 降级为混合模式,双路径同时执行 | 可能多花时间,但结果更全面 |
| **Analyst 失败** | 输入过长/生成失败 | 截断输入后重试,仍失败返回原始数据 | 看到"分析失败,以下为原始数据" |
| **可视化失败** | 数据格式不支持/绘图错误 | 跳过图表,仅返回表格 | 报告中无图表,但文字正常 |

### 4.2 重试策略

```
重试算法: 指数退避 + 随机抖动

第 1 次失败 → 等待 1s × (0.8~1.2) → 重试
第 2 次失败 → 等待 2s × (0.8~1.2) → 重试
第 3 次失败 → 等待 4s × (0.8~1.2) → 重试
仍失败 → 进入降级逻辑

仅对以下错误重试:
  ✓ 网络超时
  ✓ API 限流 (429)
  ✓ 服务不可用 (5xx)
  ✓ 临时连接错误

不对以下错误重试(直接报错):
  ✗ 鉴权失败 (401/403)
  ✗ 参数错误 (400)
  ✗ 语法错误
  ✗ 资源不存在 (404)
```

### 4.3 限流策略

采用**令牌桶算法**限制 LLM 调用频率:
- 桶容量: `LLM_RATE_LIMIT_PER_MINUTE` (默认 60)
-  refill 速率: 每分钟填满一次
- 超出请求: 排队等待或拒绝(可配置)

## 5. 数据流

### 5.1 混合模式完整数据流

```
用户输入: "分析茅台2023年财报,对比行业,引用研报"
│
├─→ Orchestrator._route(query)
│     └─→ LLM 路由决策 → mode="hybrid"
│
├─→ [并行执行]
│    ├─→ SQL Agent.invoke(query)
│    │    ├─→ Schema Agent.get_schema() → 表结构描述
│    │    ├─→ LLM 生成 SQL → "SELECT ... FROM financial_statements ..."
│    │    ├─→ Executor.safe_execute(sql)
│    │    │    ├─→ 第1层: 关键字过滤 ✓
│    │    │    ├─→ 第2层: 语法校验 ✓
│    │    │    ├─→ 第3层: 只读事务 ✓
│    │    │    ├─→ 第4层: 行数限制 ✓
│    │    │    ├─→ 第5层: 超时控制 ✓
│    │    │    └─→ SQLite 执行 → 结果集
│    │    └─→ 返回: SQL 结果表格 (字符串)
│    │
│    └─→ Retriever Agent.invoke(query)
│         ├─→ VectorStore.similarity_search(query, k=5)
│         │    ├─→ 通义 Embedding → query_vector (1536维)
│         │    ├─→ FAISS 相似度搜索 → top-5 文档
│         │    └─→ (可选) MMR 重排 → 提升多样性
│         └─→ 返回: 5 个文档片段 (带来源/页数/相似度)
│
├─→ Analyst Agent.invoke(sql_result + rag_results)
│    ├─→ 构造 prompt: 数据 + 证据 + 分析要求
│    └─→ LLM 生成 → Markdown 投研报告
│
├─→ Visualizer.generate(sql_result)
│    ├─→ 分析数据结构 → 判定为"时间序列"
│    └─→ 生成 Plotly 折线图 JSON
│
└─→ 整合输出: Markdown 报告 + 图表 JSON
```

### 5.2 数据格式契约

各 Agent 之间的输入输出格式通过 Pydantic 模型定义:

| 数据结构 | 字段 | 说明 |
|---------|------|------|
| `SQLResult` | `sql: str`, `columns: list[str]`, `rows: list[list]`, `row_count: int` | SQL 执行结果 |
| `RAGResult` | `chunks: list[Chunk]` | 召回文档列表 |
| `Chunk` | `content: str`, `source: str`, `page: int`, `score: float` | 单个文档片段 |
| `Report` | `markdown: str`, `chart_json: dict \| None` | 最终投研报告 |

## 6. 关键设计决策

### 6.1 为什么用 LangGraph 而不是手写编排?

| 方案 | 优点 | 缺点 |
|------|------|------|
| **LangGraph** | 内置状态管理、事件流、持久化、中断恢复 | 学习成本略高 |
| **手写状态机** | 完全可控,灵活度最高 | 工作量大,易出 bug |
| **纯 Chain** | 简单直接 | 不支持多轮工具调用 |

选择 LangGraph 的原因:
1. `create_agent` 开箱即用,自带 ReAct 循环
2. `astream_events` 统一事件流,流式输出轻松实现
3. 状态管理内置,不用自己维护上下文
4. 旅行项目已验证可用,迁移成本低

### 6.2 为什么用 SQLite 而不是 MySQL/PostgreSQL?

| 维度 | SQLite | MySQL | PostgreSQL |
|------|--------|-------|------------|
| 部署成本 | 零(单文件) | 需安装服务 | 需安装服务 |
| 学习成本 | 低 | 中 | 中高 |
| 并发能力 | 读好写差 | 好 | 好 |
| 适用规模 | < 10GB | < 1TB | 无上限 |

项目初期用 SQLite 足够,数据量上去后可无缝迁移到 PostgreSQL(见 [部署指南](../deployment/DEPLOYMENT.md#数据库迁移))。

### 6.3 为什么用 FAISS 而不是 Milvus/Qdrant?

| 维度 | FAISS | Milvus | Qdrant |
|------|-------|--------|--------|
| 部署成本 | 零(本地库) | 需 Docker 集群 | 需 Docker |
| 学习成本 | 低 | 高 | 中 |
| 向量规模 | < 100 万 | 亿级 | 亿级 |
| 分布式 | 不支持 | 支持 | 支持 |

项目初期 1 万份文档以内 FAISS 完全够用,且零运维成本。规模上去后可迁移(见 [部署指南](../deployment/DEPLOYMENT.md#向量库扩展))。

## 7. 扩展点

架构预留了以下扩展接口:

1. **新增数据 Agent** — 只需继承 `SpecialistAgent`,注册为 Tool 即可
2. **新增文档格式** — 实现 `BaseLoader` 接口,注册到 `doc_loader.py`
3. **切换 LLM** — 只需修改 `config.py` 中的 LLM 工厂函数
4. **切换向量库** — 实现 `BaseVectorStore` 接口,替换 `vector_store.py`
5. **新增可视化图表** — 在 `visualizer.py` 中添加图表类型和判定逻辑

详细扩展指南见 [扩展开发指南](../extend/EXTEND_GUIDE.md)。
